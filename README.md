3. 正确做法：训练用「蒸馏后的上下文」，不是原样 20k+
微调学的是：在这类约束下如何写规划，不是把 10k+ system 逐字背进显存。

建议拆成三层：

A. System（10k～13k）→ 压成 500～1500 tokens 的「训练版规则」

固定原则、输出格式、硬性边界写成短规则
重复模板、长说明、少用条款移出训练输入（或做成检索文档）
目标：让模型内化规则，而不是每条样本都带全书
B. 动态输入（5k～8k）→ 压到 2k～4k

必留：问题、问题理解、关键边界、与本题相关的量表/口径摘要
SQL 样例：只留 1～3 条最相关，不要全库
量表/skill：留「决策相关片段」，不要全文
C. 输出（2.5k～4k）→ 尽量完整保留 gold

规划是学习目标，不要乱砍
若仍太长，可固定结构（阶段/步骤/检查点），略压缩套话，不删关键动作
训练时较可行的目标长度：

输入（含短 system）≈ 3k～6k
输出 ≈ 2.5k～4k
cutoff_len ≈ 6k～8k（优先 3B）；稳了再试略加长或上 7B
这样 Qwen2.5-3B-Instruct + QLoRA 才和你的硬件匹配。

4. 和「线上仍用长 prompt」如何兼容
可以两套上下文：

阶段	上下文
训练 / 本地推理
短 system + 压缩输入
线上若仍要长 system
长 prompt 可继续用大模型 API；或检索补全细节
若线上也必须本地小模型吃满 20k+：16GB 推理都吃力，更不必说训练。更现实的是：小模型吃压缩版，细节用检索补。
